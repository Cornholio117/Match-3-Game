## Sprites and the gem atlas (Week 3, Thu)
- Why an atlas: all gem sprites packed into one texture so Unity draws them in one batch (fewer draw calls); budget is 50 batches or fewer (R5.7, PERF_LOG). Phones have limited memory and CPU/GPU time, so big textures and many draw calls hurt more than on a PC.
- Gem art: your 7 designs, 5 in use (Emerald, Ice, Magma, Amethyst, Gold); Moon Rock and Stardust Quartz kept for the 6th/7th colour stretch. No-glow versions. Resized from ~768 px to 256×256 on a transparent square (about 600 KB → 55 KB each). Only PNGs in the repo; PSDs stay local. Art rights confirmed by the author.
- Sprite import: Sprite (2D and UI), Pixels Per Unit 256 (one gem = 1 world unit, so the 8×8 board is 8 units wide), no mipmaps, **source textures uncompressed** (the atlas does the single ASTC compression; compressing twice loses quality and Unity warns).
- Atlas: `Assets/_Project/Art/Atlases/SPR_Atlas_Gems.spriteatlasv2`, built-in delivery (`includeInBuild`), padding 4 + alpha dilation (no colour bleeding), no rotation, ASTC 6x6 on Android, ASTC 4x4 on iOS. Generated by `SpriteAtlasPrebuildGenerator` (Editor, runs before every build). Sprite Packer mode must be V2 (Disabled packs nothing): read back as `SpriteAtlasV2`.
- How it was done by hand before: artists exported sprite sheets (grid in Photoshop) and sliced them in Unity's Sprite Editor; later tools like TexturePacker packed sheets automatically; Unity 2017 added the legacy "Packing Tag" on each texture, then Sprite Atlas assets (V1, then V2 `.spriteatlasv2`). Manual V2 steps: Create > 2D > Sprite Atlas, drag the gem folder into "Objects for Packing", set padding/compression, tick Include in Build, click Pack Preview.

## Combo: two special gems swapped (Week 4, Fri)
- Rule: swapping two special gems is **always legal**, even with the same colour and no match, if they are neighbours and inside the board (`SwapRules`; one special + one normal still needs a run). It is the one exception to "specials fire only when matched".
- Effect (for line gems, the only special so far): the swap fires a **combo** instead of the gems' own lines: both gems are used up and the first wave clears the **row and the column through the cell the player moved to** (the second swap cell). Any other special gem caught in that cross fires too (chain reaction). `TurnResolver.Resolve(..., combo: true)`; `BoardGame.TrySwap` detects "both gems special" before swapping. Then fall, refill and the normal cascade loop continue.
- Prediction pictures: two line gems side by side on a 5×5 board → 9 cells (row 5 + column 4, the crossing counted once); a third line gem on the column → 13 cells (it fires its row for 4 more).
- Combos for the diagonal and shockwave gems will be defined when those gems exist (each pair of kinds needs its own rule).
- No view change: the view already plays the swap and then the recorded steps.
- Proof the tests bite: with the two "used up" lines removed (so each combo gem fires its own line too), 3 combo tests fail. 172 tests pass.

## Line gem, logic (Week 4, Thu)
- A board cell now holds a colour **and** a kind (`PieceKind`: Normal, LineHorizontal, LineVertical): `BoardModel.GetKind`, `SetPiece(position, color, kind)`; `SetPiece(position, color)` makes a normal gem; `Swap` and `BoardGravity` carry the kind with the gem.
- Creation (in `TurnResolver`): a run of **exactly 4** makes a line gem of the run's colour (horizontal run → clears its row, vertical run → its column). It appears on the cell the player moved to if that cell is in the run; otherwise (cascades) on the run's lower-left cell. The other three gems clear. The new gem is protected from clearing in the wave that creates it, and must be made on a normal gem (so an existing special still fires). Runs of 5+ just clear for now.
- Firing: every special among the cleared cells clears its whole row or column; special gems inside that line fire too, in a queue until nothing new is added (**chain reaction**), bounded by the cascade limit. Prediction pictures: 3-run with a vertical special = 6 cells; plus a second (horizontal) special on the column = 10 cells.
- A new `Create` step records the conversion for the view; `TurnResult` also counts `SpecialsCreated` and `SpecialsFired`.
- `GridPosition.GetHashCode` now uses a fixed formula: `HashCode.Combine` is randomised per program run, which would make the iteration order of cell sets (and so the order of animation steps) differ between sessions.
- Proof the tests bite: with the chain-reaction line disabled, exactly the 10-cell test fails. A mistake worth remembering: two of my own tests failed at first because I used the wrong coordinates (rows are written top to bottom, `y = 0` is the last line).

## Board view and touch (Week 4, Wed)
- Model/view split in practice (P1): `BoardGame.TrySwap` validates, swaps and resolves the whole turn instantly, recording `BoardStep`s; `BoardView` then plays the swap and the steps as animations. Consecutive steps of the same kind (all clears, all falls, all spawns) play together. Spawns start one board-height above their cell so new gems drop in from above.
- `BoardController` owns the busy flag; `BoardInputHandler` only reports "swap these two cells" (it never decides if a swap is allowed). While busy, new swipes are ignored. Swipes off the board edge are ignored.
- `SwipeMath.TryGetDirection(dx, dy, minDistance)`: the longer axis wins, a tie counts as horizontal, shorter than the minimum is no swipe. The finger position is mapped through the camera onto the board plane (z = 0).
- Input System: `EnhancedTouchSupport.Enable()`, `Touch.onFingerDown/Move/Up`; `TouchSimulation.Enable()` in the Editor so the mouse acts as a finger. Subscribe in `OnEnable`, unsubscribe in `OnDisable`. One swap per touch.
- Pooling: `PiecePool` (`ObjectPool<PieceView>`, prewarm 128) and `PieceView : IPoolable` that resets scale and colour on reuse. Gotcha: when Play mode ends Unity resets all pools, calling `actionOnDestroy` on gems already destroyed, so the destroy callback must check `piece != null`.
- Config: `PieceSet` ScriptableObject maps colour → sprite (`SO_PieceSet`: Green=Emerald, Blue=Ice, Red=Magma, Purple=Amethyst, Yellow=Gold). New scene `Level.unity` (copy of Boot, R4 hierarchy) with the `PieceView` prefab.
- Verified in the Editor with a 20-turn probe (valid, invalid and double swipes): view always matched the model, no gem missing or off its cell, exactly 64 active gems at the end (no pool leak). Animation code cannot be unit-tested, so it is verified by playing it.
- Verified on the Galaxy S21 FE (development build, 67 MB): real swipes sent with `adb shell input swipe` cleared gems and cascaded; three swipes that must be ignored (off the edge, starting outside the board, too short) changed 0 pixels; 12 random swipes plus a double swipe ended with 64 of 64 cells holding a gem and no exceptions in the phone's log.
- Not done yet: score and moves (week 5), special gems, the "no valid moves" reshuffle.
- Allocation check (Thursday): measured per-frame garbage during a turn against idle frames. The first version cost **48 B per frame**: `await Awaitable.NextFrameAsync(destroyCancellationToken)` registers a new cancellation callback on every await, and that allocates. Fix: `await Awaitable.NextFrameAsync();` then `destroyCancellationToken.ThrowIfCancellationRequested();` → **0 B** difference from idle (see PERF_LOG.md). Lesson: a small per-frame allocation is easy to miss by eye, so measure instead of assuming. Compare against an idle baseline, because the Editor allocates about 22 KB per frame by itself.

## Cascades (Week 4, Tue)
- A turn after a swap: **find runs, clear the distinct cells, gravity, refill, repeat** until no runs remain. `TurnResolver.Resolve(board, random, colorCount, steps)` runs the loop and returns a `TurnResult` (cascades = clear waves, cells cleared, hit the limit?). `DefaultMaxCascades = 50` stops a pathological refill from looping forever (core risk in the GDD).
- The model records **steps** (`BoardStep`: Clear, Fall from→to, Spawn) in a list the caller passes in and reuses; the view will play them back as animations later (P1): logic is instant and testable, animation is separate.
- `BoardGravity.Apply`: per column, walk up and drop each gem to the lowest free cell (`restingY`); order in a column never changes; returns how many moved (the prediction picture: 7 falls). `BoardRefill.Apply`: fills every empty cell with a seeded random colour (`random.Next(colorCount) + 1`, since 0 is None); unlike the first fill it **may** create runs, which is how cascades start. Picture counts: 20 cells − 9 gems = 11 spawns.
- Same seed + same board = same steps (replayable). Tests use `ScriptedRandom` (a fake `IRandom` returning a fixed list) to force an exact cascade, and `BoardBuilder.ToRows` to read a board back as a picture.
- Proof the tests bite: with the `restingY++` line commented out, 4 tests fail (including the prediction picture and the forced cascade). 130 tests pass.

## Swap and match (Week 4, Mon)
- Coordinates: `GridPosition(x, y)`, x = column, y counts **up from the bottom**; `(0,0)` is bottom-left. Test pictures are written top to bottom (last row is y = 0), so a picture row and a y value are mirrored; this is a classic source of bugs.
- `MatchFinder.Find(board, results)` walks every row, then every column, tracking the current run of one colour; a run of 3 or more becomes a `Match` (colour, start, direction Right or Up, length). Reading one step past the end (as `None`) closes a run touching the board's edge. An L or T gem belongs to two runs, so clear the **distinct** cells (picture 2: 2 runs, 5 cells). The result list is passed in and reused (no allocation per call).
- `MatchFinder.IsPartOfMatch(board, position)` checks one cell by counting same-colour neighbours each way (across, up and down); `SwapRules.IsValidSwap` uses it.
- `SwapRules.IsValidSwap(board, a, b)`: both cells on the board, adjacent (`IsAdjacent`), both non-empty and different colours, and the swap creates a run. It swaps, checks, and always swaps back, so it only answers a question.
- `BoardModel` gained `SetPiece` and `Swap` (the two basic operations; they do not check rules). Tests build boards from text pictures with `BoardBuilder.FromRows` ("GGG." etc.).
- Proof the tests bite: with the match finder's loop bound off by one (`i < length`), exactly the 5 edge-touching tests fail. 111 tests pass.

## Board model (Week 4, Sun)
- `BoardModel` (`Game.Core.Board`) stores the 8×8 `PieceColor[,]` and fills it; swapping and matching are separate classes (one job each, R1.5). `PieceColor`: None (empty) + Green, Blue, Red, Purple, Yellow, White, Pink (your 7 gems); a level uses the first 4 to 7. Cell (0,0) is bottom-left; `GetPiece` throws outside the board.
- `Fill(random, colorCount)` goes bottom-left to top-right. For each cell it bans a colour when the **two cells to the left** or the **two cells below** already match (`first == second`), then picks randomly from the rest. With at least 3 colours a choice always remains (at most 2 are banned), so a starting board never has a row or column of three.
- Randomness: `IRandom` (`Game.Core.Common`) + `SeededRandom(seed)`. The same seed always gives the same board, so any level or bug can be replayed (R6.3).
- Tests (13 for the board, 2 for the random): same seed same board, different seeds differ, 200 seeds × colour counts 3/4/5/7 never start with a run of three, only the first N colours used, bad sizes and colour counts throw. Proof the tests bite: with the ban line disabled, exactly the four "never starts with a run" tests fail. 82 tests pass.

## Unity lifecycle and ScriptableObjects (Week 3, Sun)
- Order: `Awake` (set yourself up; once per object) → `OnEnable` (subscribe) → `Start` (use other objects; all `Awake`s have run) → `Update` (only if something changes every frame) → `OnDisable` (unsubscribe) → `OnDestroy`.
- `OnEnable`/`OnDisable` run on every activate/deactivate (so pooled objects hit them many times); `Awake`/`OnDestroy` run once. Every `+=` needs its `-=`.
- ScriptableObject = an asset file of data, edited in the Inspector. One class (`LevelConfig`), many assets (`SO_Level_01` … `SO_Level_20`). Private serialized fields with read-only properties; config is read-only at runtime, state lives in models (`new MovesModel(config.Moves)`). Naming: `SO_` prefix, folder `_Project/ScriptableObjects` (R3.3, P7).
- Code: `Game.Runtime.Config.LevelConfig`; assets `SO_Level_01` (20 moves, 1000 target) and `SO_Level_02` (18 moves, 1500 target). Checked: `MovesModel(level2.Moves).Remaining == 18`.

## MVP and dependency injection (Week 2, Thu)
- **MVP:** Model = data and rules, no UI (`MovesModel`). View = only displays, no logic (a label with `ShowMoves`). Presenter = plain C# that listens to the model's events and tells the view what to show. Subscribe in `Enable`, unsubscribe in `Disable`.
- The presenter takes an interface (`IMovesView`), so a test can hand it a fake view and check what it was asked to show; no scene needed.
- Formatting belongs to the view, but a change like "5 / 20" needs the total, so the interface and presenter gain a parameter too.
- **DI:** dependencies are handed in (constructor), not fetched. **Service locator:** the class reaches into a global registry; needs are hidden and tests need global setup. Project rule: DI only, no locator, no static singleton (P6, R1.7).
- `Bootstrap` (top of the Boot scene) creates the model, view and presenter and passes them in.

**Two-minute explanation (practise out loud):**
"I'd use MVP. The model holds the data and rules with no UI, like `MovesModel`. The view only displays things, like a label with a `ShowMoves` method. The presenter is plain C# that listens to the model's events and tells the view what to show, so I can test it with a fake view. The presenter doesn't create or look up its model and view; they're handed in through its constructor, which is dependency injection, and a single Bootstrap creates everything and passes it in. I avoid a service locator because the dependencies would be hidden and tests would need global setup."

## Pool and Factory (Week 2, Wed)
- Unity's `ObjectPool<T>` (`UnityEngine.Pool`) takes four callbacks: `createFunc` (a `Func`, makes a new one), `actionOnGet`, `actionOnRelease`, `actionOnDestroy` (`Action`s), plus `defaultCapacity` and `maxSize` (spare ones beyond it are destroyed). Use `Get()` / `Release()`.
- Reset all state when an object goes back (our `OnDespawned`, P4) so the shelf only holds clean ones.
- Factory = one class owns the creation details; callers say `Create(color, position)` and `Recycle(piece)`. Behind an interface (`IPieceFactory`) so tests can use a fake; sprites come from a config, so a new gem type changes config, not the factory. The board knows nothing about pooling.
- Measured (Editor, 50 objects/frame): `Instantiate`/`Destroy` 2.0 KB and 0.55 ms → pool 0 B and 0.25 ms (see PERF_LOG.md). Compare the same Profiler row in both modes, not different rows.

## State machine (Week 2, Tue)
- The game is in exactly one state at a time (Boot, Menu, Level, Win), so impossible combinations of bools can't happen.
- `IState` = `Enter()` + `Exit()`; `StateMachine.ChangeState(next)` = guard (same state → do nothing), `Current?.Exit()`, set `Current`, `Current.Enter()`. Leave first, then arrive. The first call has no old state to exit.
- The machine only knows `IState` (DIP), so adding a `ShopState` never touches it. Class-based, not the Animator; one machine per concern (P2).
- Code: `Game.Core.Flow` (`IState`, `StateMachine`); tests use a `LoggingState` that records Enter/Exit to check the order.

## Observer and Command (Week 2, Mon)
- Observer = events / the notice board: one thing announces, many react, the announcer doesn't know them (`MovesChanged`, `EventBus`).
- Command = an action as an object that knows how to `Execute()` and `Undo()` and remembers its own values (`AddScoreCommand(score, points)`). Keep the history in a `Stack`: newest undone first.
- Other uses: input queue, replays, tutorials, booster use. Real match-3 undo must restore the board state (cascades change many cells), not just "swap again".
- `private readonly` = hidden from outside + set once in the constructor, so a command can't lose track of what it did.

## SOLID (Week 2, Sun)
- **S** Single Responsibility: one class, one job (`BoardModel` finds matches; input, view and saving live elsewhere).
- **O** Open/Closed: add behaviour without editing old code (a new booster = a new class).
- **L** Liskov Substitution: a child must work wherever its parent is expected (every booster activates the same way).
- **I** Interface Segregation: small interfaces (`IPoolable` has two methods), not one giant one.
- **D** Dependency Inversion: depend on a promise, not the concrete thing (`BoardModel` receives `IRandom`); `Bootstrap` hands in the real tools.
- Refactor example: old `MainEvents.cs` split into narration, movement switch, bridge, mantis, hands (see `Docs/Study/MainEvents_refactor.md`). Repeated code with small differences = data in a list.

## Week 1 review: things to re-check (Fri)
- Array vs List: the 8x8 board is an array (`board[x, y]`, fixed size); a `List` is for a changing count. `GridPosition` is a cell's address, not its contents.
- Interface = a list of method names a class promises (no code, many per class). Abstract class = a parent with real code plus blanks (one parent).
- Garbage fixes: `SetText("Score: {0}", score)` instead of string concatenation; `GameLog.Info` instead of `Debug.Log`.
- Async: the waiter holds a `token`; the boss holds a `source` and calls `source.Cancel()`.

## Value vs reference types (Week 1, Sun)
- `struct` = photocopy: `b = a` makes an independent copy. `Vector3`, `GridPosition`.
- `class` = two names for one object: `b = a` points to the same object. `Transform`, `GameObject`.
- `b = new ...` always makes a new, separate object, even for classes.
- Structs create no GC garbage, which is why board positions are structs.
- Why `transform.position.x = 5` is a compile error: reading `position` returns a copy.

## Boxing (Week 1, Sun)
- Boxing = a plain value (`int`, struct) gets wrapped in a heap object. That object is garbage the GC must clean up.
- Happens when a value goes into an `object` variable: `object o = score;`, `Debug.Log(coins)`, `ArrayList`.
- One call is fine. Inside code that runs every frame it adds up and causes stutters.
- Avoid with generics (`List<int>`), `IEquatable<T>` on structs, and `GameLog` instead of `Debug.Log`.

## Garbage collector and hidden allocations (Week 1, Mon)
- Heap = the counter where objects live. GC = the cleaner that pauses the game to clear unused ones. At 60 fps a frame has about 16 ms, so a pause is a visible stutter.
- Hidden garbage sources: string concatenation, `new` in `Update`, boxing, lambdas that capture variables, LINQ, `foreach` over interface-typed collections.
- Fixes: create once and reuse (`Clear()`), use a plain `for` loop, use `TMP_Text.SetText("{0}", n)`, update UI on events instead of every frame.
- Lab results: new List 88 B → 0 B; LINQ 284 B → 0 B. String snippet unresolved in the Editor (98 B); re-measure on device in week 8 (see PERF_LOG.md).
- `for` vs `foreach`: `for` shows the index and never allocates; `foreach` is shorter but allocates when the variable's type is an interface (`IEnumerable<T>`). Prefer `for` in hot paths.
- Editor numbers are for finding problems; device numbers go into the log.

## Collections cheat sheet (Week 1, Tue)

| Need | Container | Game example |
|---|---|---|
| Fixed count, access by position | Array | the 8x8 board: `board[x, y]` |
| Grows and shrinks, keeps order | `List<T>` | pieces cleared this turn |
| Each item once, fast "is it in there?" | `HashSet<T>` | cells already checked during a match search |
| Look up a value by a key | `Dictionary<K,V>` | piece colour → score or sprite |
| First in, first out (a line) | `Queue<T>` | pieces waiting to fall |
| Last in, first out (a pile) | `Stack<T>` | undo history |

- Searching a `List` one by one gets slower as it grows. `HashSet`/`Dictionary` go straight to the item, so they stay fast.
- A struct used as a set/dictionary key needs `IEquatable<T>` and `GetHashCode` (like `GridPosition`).
- Create collections once and reuse them with `Clear()` (no per-frame `new`).

## Delegates, generics and the event bus (Week 1, Wed)
- `Action` = a method with no result you can hand around (`new Ability(() => ...)`); `Action<int>` receives a value; `Func<int, bool>` answers a question (last type = the answer). Lambda `x => ...` = "takes x, does/gives ...".
- One method + a `Func` rule = many behaviours (booster `ClearWhere(cell => cell.Y == 3)`). Capturing lambdas allocate: fine for one-offs, not per-frame.
- Interface = "it can do this" (many allowed, no shared code). Abstract class = "it is this kind of thing" (one parent, shared code; `abstract` = blank each child must fill, `protected` = children may use, `override` = my version). `sealed` = nothing may inherit; our default (R2.4). Abstract + sealed is a compile error.
- Generics: `<T>` is a placeholder type (`List<T>`, `Pool<T>`). Constraints: `where T : new()`, `where T : class`, `where T : IPoolable` — the compiler then knows `T` can do that.
- Object pooling: never Instantiate/Destroy repeatedly; deactivate and reuse, and reset all state on return (OnSpawned/OnDespawned).
- Event bus: a notice board for global announcements only ("level won"). `Channel<T>` = listeners for one notice type; `EventBus` = `Dictionary<Type, object>` of channels. Publish with no listeners does nothing. For local things (a moves label) use a plain C# event instead.
- `TryGetValue(key, out var x)` is the safe dictionary lookup; the `out` variable name must not clash with a parameter name.

## Async vs coroutines (Week 1, Thu)
- Never wait with a plain pause: frames must keep rendering. Coroutine: `yield return new WaitForSeconds(2f)`. Async: `await Awaitable.WaitForSecondsAsync(2f, token)`.
- A coroutine belongs to its MonoBehaviour, so Unity stops it when the object is destroyed. An async method belongs to nobody, so it keeps running and then touches a destroyed object (`MissingReferenceException`) unless it listens to a stop signal.
- Stop signal = `CancellationToken`. In a MonoBehaviour use `destroyCancellationToken` (Unity raises it on destroy). In plain C# the caller passes a `token`; a test makes one with `CancellationTokenSource` and presses it with `source.Cancel()`.
- A cancelled wait throws `OperationCanceledException`; catch it quietly (expected), but never leave other empty catches (real bugs, e.g. a corrupted save → log and start fresh).
- Async can return a value (`Task<int>` / `Awaitable<T>`); coroutines need a callback. Avoid `async void` (R9): use `async Awaitable` and start with `_ = Method();`.
- Exercise: `FakeLevelLoader` in `AsyncLoaderTests.cs` (Task-based so it runs in EditMode; the game version uses Awaitable).

## Interfaces (Week 1, Wed — started early)
- An interface is a promise: "I have these methods". A class can promise many; it can only inherit from one parent.
- Lets tests swap real code for a fake (`IRandom` → a dice that always returns 3).

## Constructor, `readonly`, `=>` (Week 1)
- Constructor = the `Awake` of plain classes, but it takes parameters.
- `readonly` = a field that can only be set once, in the constructor. A safety lock.
- `=>` = one-line method; in a lambda it means "takes this, does that".

## Events (Week 1, Wed — started early)
- The owner shouts, listeners sign up with `+=` and sign off with `-=`.
- Always subscribe in `OnEnable` and unsubscribe in `OnDisable`, or destroyed objects stay on the list.
- C# `event` for code-to-code; `UnityEvent` only for designer-wired Inspector clicks.
