# DECISIONS.md — Technical decision log

One entry per non-obvious decision. Newest at the bottom. These double as interview talking points.

Format:
```
## D<number> — <title> (<date>)
**Decision:** what we chose
**Why:** the reason, in 1–3 lines
**Alternatives considered:** what we did not choose and why
```

---

## D1 — Unity 6.3 LTS (2026-10-30)
**Decision:** Unity 6.3 LTS, Universal 2D (URP 2D Renderer).
**Why:** Mobile studios run live games on LTS; SDKs (Addressables, IAP, ads) are tested hardest against LTS.
**Alternatives considered:** Unity 6.6 (newer features, but not LTS).

## D2 — Logic in plain C#, views in MonoBehaviours (2026-10-30)
**Decision:** Game rules live in `Game.Core` with no MonoBehaviours; views only animate results.
**Why:** Fast, deterministic EditMode tests; logic can be explained and reviewed without a scene.
**Alternatives considered:** Logic inside MonoBehaviours (harder to test, couples timing to animation).

## D3 — No third-party frameworks at start (2026-10-30)
**Decision:** Built-in `Awaitable`, `ObjectPool<T>`, manual composition root. No DOTween/UniTask/VContainer yet.
**Why:** Shows understanding of the fundamentals; fewer dependencies to explain or debug.
**Alternatives considered:** Adding them later is allowed — log a new decision when we do.

## D4 — AI tooling: Unity CLI + official Claude Code plugin (2026-10-30)
**Decision:** Claude drives the Editor through the Unity CLI and Pipeline package, with Unity's `/unity:` skills.
**Why:** Unity's current recommended path; the in-Editor AI Assistant MCP server is deprecated.
**Alternatives considered:** Third-party Unity MCP packages (still work, but one bridge per project).

## D5 — Assembly layout and generated Boot scene (2026-10-30)
**Decision:** Five asmdefs: `Game.Core` (no engine references), `Game.Runtime`, `Game.Editor`, and two test assemblies. The Boot scene is generated by `Tools/Match3/Create Boot Scene` instead of being hand-built.
**Why:** `noEngineReferences` makes it impossible for Core to depend on UnityEngine, and separate assemblies keep recompiles fast. A builder script makes the R4 hierarchy reproducible and avoids hand-editing scene YAML.
**Alternatives considered:** One assembly for everything (no enforced boundary); hand-written scene YAML (fragile).
